# 本体平台功能现状与缺口梳理（大白话版）

> 写给第一次接触本体平台的同学。读完你会知道：它是干嘛的、现在已经能干什么、还欠什么没干。
> 依据：`backend/cmx-ontology` 代码实测（2026-09-08）、全量测试报告（2026-08-31，351 项测试全过）、完整实现方案与待办清单（2026-09-07）。

---

## 一、这是个啥？

一句话：**本体平台是整个公司的"数据地图 + 办事大厅"**。

打个比方。一家大公司里，各部门各管一摊：销售系统里有客户，财务系统里有科目，仓库系统里有物料。同一个"客户"在三个系统里叫三个名字、三套格式，谁也说不清全公司到底有哪些"东西"、它们之间是什么关系。

本体平台就是来画这张**全公司统一的数据地图**的：

- 地图上先登记"有哪些种类的地点"——客户、订单、物料……（这叫**建模**）；
- 然后把真实数据一份份搬进来挂在地图上（这叫**对象数据**）；
- 地点之间有道路相连（客户"下单"了订单，这叫**关系**）；
- 地图上还能装"办事按钮"——点一下就能发起审批、生成报表（这叫**动作**）。

它是**连接层**，不是又一个业务系统：它不替代销售系统、财务系统，而是把它们的数据和操作统一到一张地图上，别人都按地图来找数据、办事情。

技术上它是一个独立的 Rust 微服务，端口 `:8097`，数据存 PostgreSQL。浏览器打开 `http://127.0.0.1:8097/` 就能用。

## 二、先看懂几个词（术语小词典）

| 术语 | 大白话解释 |
| --- | --- |
| **本体（Ontology）** | 那张"企业数据地图"本身：全公司有哪些东西、什么关系，统一定义成一整套。 |
| **对象类型（ObjectType）** | 地图上的"地点种类"，即模板。比如"客户"这个模板：有哪些字段（名称、税号……）、主键是什么。 |
| **对象（实例）** | 按模板填出来的一条真实数据。比如客户"北京首钢有限公司"就是"客户"类型下的一个对象。 |
| **属性 / pk / title / props** | 属性就是字段。pk 是主键（身份证号，唯一标识）；title 是标题（给人看的名字，如客户简称）；props 是"全部家当"——所有字段值打包存在一个 JSON 里，不建一堆数据库列。 |
| **关系（LinkType / 边）** | 地图上的"道路"。有方向（谁指向谁）、有基数（一对一 / 一对多 / 多对多）、两端各有角色名（如"订单—[买家]→客户"）。 |
| **接口（Interface）** | 横切能力标签，**不是网络接口**。比如"可开票"是个接口，客户、供应商都可以挂这个标签，表示它们都有开票相关的那组字段。 |
| **共享属性（SharedProperty）** | 全局标准字段：一处定义、多处引用。比如"创建时间"定义一次，所有对象类型都引用它，改一处全生效。 |
| **动作（ActionType）** | 地图上的"办事按钮"：给参数 → 按规则校验 → 改哪些数据 → 办完通知谁。比如"提交退租申请"就是一个动作。 |
| **函数（Function）** | 一段可复用的**读侧计算**，用 FEEL 小语言写的表达式，配置即生效，不用改代码。 |
| **FEEL** | 一种很简单的表达式语言（类似 Excel 公式），比如 `金额 > 0`、`单价 * 数量`。平台用它写校验规则和计算。 |
| **对象集（ObjectSet）** | 一次查询的"导航指令"：从哪类对象出发、按什么条件过滤、顺着关系走到哪。最终编译成**一条** SQL 执行。 |
| **SearchAround（顺藤摸瓜）** | 从一个对象顺着关系跳到相关对象。比如从"某客户"一跳看到它名下所有订单。 |
| **发布 / 版本** | 把整套地图定义"拍照存档"，版本号只增不改。改错了可以回溯到旧照片。 |
| **乐观锁** | 防止两个人同时改同一条数据互相覆盖：提交时要带上"我看到的是哪个版本"，对不上就报冲突让你刷新重来。 |
| **漏斗（Funnel）** | 数据搬运通道：从外部数据源按映射规则灌进来，合格的落库，不合格的进隔离区。 |
| **隔离区（Quarantine）** | 同步时的"不合格品区"：坏数据不直接扔掉也不混进好数据，先搁这儿等人工复核。 |
| **发件箱（Outbox）** | 办完事后要发的"通知"先写进一张待发清单（和数据改动同一个事务，保证不丢），后台再挨个真正发出去。 |
| **副作用（SideEffect）** | 动作办完正事之后的"附带动作"：起审批流、算报表、调外部地址（Webhook）、发通知。 |
| **SSE** | 服务器向浏览器单向"广播"的通道。本体里数据一变，页面能立刻收到消息刷新。 |
| **OSDK** | 一键生成给前端用的 TypeScript 代码包（SDK），前端调本体接口就有类型提示，不用手写。 |
| **DCT / DOC / MDM** | 都是隔壁兄弟服务：DCT 是数据字典（字段标准）、DOC 是单据模型、MDM 是主数据管理（客户 / 物料这些基准数据的官方来源）。 |

## 三、现在已经支持的功能

> 以下都有代码和真机测试背书：2026-08-31 全量测试 **351 项全部通过**（Rust 单元测试 54 + 后端接口测试 158 + 前端页面测试 139），对外提供 50 多个 API 接口。

### 3.1 画地图：可视化建模（设计工作台）

浏览器里的四区工作台：左边是元素树（七类元素分组），中间是大画布，右边是属性面板，顶部是工具栏。

- ✅ **七类元素全支持增删改**：对象类型、关系、接口、共享属性、动作、函数，外加策略。
- ✅ **画布即地图**：本体图组件 `<cmx-ontology-graph>` 渲染 ER 图——每个对象类型是一张"富卡片"（显示字段清单、主键◇、标题⌾、索引⚡、必填\*），关系是带基数符号的连线，接口挂接是虚线。
- ✅ **拖拽 / 拉线建关系**：从一张卡片边缘的连接点拖到另一张，弹出气泡补上基数和角色名，关系就建好了。
- ✅ **属性编辑面板**：选中什么就能改什么，字段级属性（类型、主键、必填、索引等）在卡片里直接编辑。
- ✅ **画布体验**：拖拽节点摆位、连线避让、线段微调、一键自动重排，都有动效且不破坏已有布局。

### 3.2 存数据：对象实例与关系

- ✅ 对象的增删改查（单条 / 批量），数据落在按类型自动生成的物理表里（`oo_<类型>`）。
- ✅ 修改带**乐观锁**：带 `expectedUpdatedAt` 提交，两人撞车会明确报冲突。
- ✅ 关系（边）统一存一张边表，对象的增删改会自动维护它的边（删对象，相关的线也清掉）。
- ✅ 层块结构：单据的"明细行"以嵌套数组形式折叠在对象内部，一张单据就是一个对象。

**物理表（`oo_<类型>`）是怎么来的？——"写时自动建"，不用手动建**（2026-09-09 代码实测补充）

对象数据每类一张 PG 物理表，表名 `oo_<类型apiName>`（如 `oo_Customer`）。这张表**不是**在设计器新建对象类型时就建的——新建类型只往定义表 `om_object_type` 写一行定义；物理表是**第一次往该类型写数据时自动建**的（幂等 `CREATE TABLE IF NOT EXISTS`，重复调也不会出错，建表逻辑统一在 `cmx-onto-store-pg/src/object_store.rs` 的 `ensure_object_table`）。四个入口会触发建表，全部是"写数据"场景：

| 入口（前缀 `/api/onto/v1` 省略） | 说明 |
| --- | --- |
| `POST /objects/{type}` | 单条写入前建 |
| `POST /objects/{type}/batch` | 批量写入前建；**传空数组 `[]` 就只建表不写数**，可当"建表接口"用 |
| `POST /import/dct` | 字典导入种数据前建 |
| `POST /funnel/sync/{type}` | 漏斗同步灌数前建 |

几条实用结论：

- **表结构是固定的**：`pk / title / props(JSON) / created_at / updated_at`，所有属性值都打包在 `props` 一个 JSON 字段里。所以**给类型加字段不需要动物理表**，纯定义层操作。
- **只建了类型、从没写过数据时，查询会报错**：对象浏览器 / 360 的列表查询走纯读接口（`/object-sets/load`、`/object-sets/aggregate`），不会顺手建表，表不存在就报 `relation "oo_xxx" does not exist`。想让新类型"可查询"，先写一条数据（或对 batch 接口传空数组）即可。
- **删除类型不删表**：删类型只删定义行，`oo_xxx` 表和里面的数据会留下（孤儿表）；用同名重建类型会接着用旧表，旧数据还在。
- **表名有规矩**：类型 apiName 必须是合法标识符（字母 / 下划线开头，只含字母数字下划线），否则拒绝——防 SQL 注入。

### 3.3 查数据：对象集查询

- ✅ 对象集代数：起点 + 过滤 + SearchAround + 并集 / 交集 / 差集，编译成**一条** SQL，一次往返出结果。
- ✅ 聚合：计数、分组计数、分组求和。
- ✅ 分页（每页最多 1000 条）。

### 3.4 办事情：动作引擎（这是平台的招牌）

- ✅ **动作执行闭环**：参数校验（FEEL 规则，不合法直接拦）→ 按声明生成五种编辑原子（建 / 改 / 删 / 加关系 / 断关系）→ **单个事务**落库 → 写审计日志（谁在什么时候干了什么，可查）。
- ✅ **试算（dry-run）**：先"预演"一遍看会改什么，不真落库。
- ✅ **权限门**：每个动作可配置谁能执行，执行前强校验。
- ✅ **四种副作用，且全部可在设计台可视化配置**：
  - **起审批流**——联动流程引擎（flowengine）真实创建流程实例（已真机验证：本体的动作真把流程实例建出来了）；
  - **算报表**——联动报表服务（cmx-report）真实计算并落库（已真机验证）；
  - **Webhook**——回调外部地址（带白名单防滥用）；
  - **通知**——按模板发通知。
- ✅ **可靠投递**：副作用先进发件箱（和业务数据同事务，绝不丢），后台派发器逐条投递、失败标记、幂等重试。
- ✅ **动作模板**：内置模板库（如旗舰模板"关账联动"——一个按钮同时起关账审批流 + 算关账报表），新建动作可从模板一键实例化。

### 3.5 自动算：函数计算

- ✅ FEEL 表达式求值，函数分五类：查询、派生属性、校验、动作逻辑、聚合。
- ✅ 运行台可在线试算函数。

### 3.6 搬数据：数据集成

- ✅ **漏斗同步**：配置"源 → 字段映射"规则，一键全量同步进本体；校验失败的行自动进**隔离区**，不污染好数据，可人工复核。
- ✅ **反向导入**：把隔壁字典（DCT）、单据模型（DOC）的定义一键转成本体的对象类型 + 关系 + 种子数据，不用手工重录。
- ✅ 同步进度可查（管道状态接口）。

### 3.7 管权限：安全

- ✅ 策略配置：行级过滤（哪些行的数据你看不见）、字段脱敏（手机号只给你看后四位那种）、动作禁用清单。
- ✅ 带"安全门"的查询接口：查询结果按策略先过滤再返回。

### 3.8 存档：发布与版本

- ✅ 一键发布：整套定义拍快照（带指纹校验），版本号只增不减。
- ✅ 版本列表、任意历史版本可回看。

### 3.9 给程序员用的接口

- ✅ REST API（`/api/onto/v1` 前缀）+ OpenAPI/Swagger 文档。
- ✅ OSDK：一条命令生成强类型 TypeScript 客户端（生成的代码过严格编译检查）。
- ✅ SSE 事件流：数据变更实时广播。
- ✅ API Key 认证。

### 3.10 和别家的打通

- ✅ **门户集成**：三个工作台（设计 / 浏览 / 客户360）已挂进门户菜单，走统一登录和反向代理。
- ✅ **流程引擎 / 报表服务联动**：动作副作用真打通（见 3.4）。
- ✅ 动作配置界面的下拉选择器（选哪个流程、哪张报表）由本体代理查询隔壁服务自动填充。

### 3.11 看数据：对象浏览器与客户360

- ✅ **对象浏览器**：不懂 SQL 也能查——点选对象类型、拼过滤条件、顺着关系一跳钻取，图谱化展示。
- ✅ **Workshop（客户360）**：选中一个对象，属性卡 + 关系区 + 可执行的动作一屏展示，办完事自动刷新——业务人员的"一站式工作台"。

## 四、还缺哪些功能

缺口分三档（来自待办清单的优先级）+ 一类"压根还没做"的能力。

### 4.1 🔴 紧急的安全债（P0，建议尽快修）

| 编号 | 问题 | 大白话 |
| --- | --- | --- |
| S1 | 身份可自报 | 某种认证模式下，调用方"自己说自己是谁"就能绕过行级权限和动作禁令——相当于保安不查证件，你说你是谁就放谁进。 |
| S2 | 漏斗的 SQL 注入面 | 数据同步有一处是拼接 SQL 且查询语句任意填，是全平台唯一不走参数化查询的地方——相当于门都上了锁，就这扇窗没关。 |

### 4.2 🟡 排期的自动化缺口（P1）——"门修好了，搬运工没有"

平台把各种集成的"接口插座"都装好了，但缺**主动去插电的机制**：

| 编号 | 缺什么 | 大白话 |
| --- | --- | --- |
| T1 | 定时调度器 | 现在所有同步 / 派发都要人点或外部调接口才动，平台自己不会"到点干活"（全仓没有任何定时任务）。 |
| T2 | MDM 审批完自动同步 | 主数据审批通过了，还得人来点同步；缺"审批通过 → 自动触发搬运"这段接线。 |
| T3 | 审批结果回写本体 | 动作能把"起流程"发出去，但**流程审完通过 / 驳回，结果不会自动回来改对象数据**——出去的单程票，没有回程。 |
| T4 | 增量同步 | 现在搬运是"整批替换"，不能只搬上次之后变化的，数据量大时费劲。 |
| T7 | 本体 → MDM 回写 | 只有 MDM 流向本体（单向），本体里改了数据传不回主数据系统。 |

### 4.3 🟢 有空再说的优化（P2）

| 编号 | 问题 | 大白话 |
| --- | --- | --- |
| T5 | 异步任务中心 | 大任务（大同步 / 大动作）现在是"原地等结果"，没有进度条、暂停、断点续跑。 |
| T6 | 消息队列入站 | 不能从消息队列（Kafka 等）收活儿，只能靠 HTTP 调接口。 |
| Q1 | JSONB 查询没索引 | 字段值都塞在一个 JSON 大字段里，按字段过滤是全表翻，数据多了会慢。 |
| Q2 | 删对象清边可能误删 | 清理关系线时按业务键全局匹配，理论上可能误删别人的线。 |
| Q3 | 发布并发撞车 | 两人同时点发布，版本号可能撞。 |
| Q4 | 金额精度 | FEEL 计算用浮点数，算钱可能出现 0.1 + 0.2 ≠ 0.3 类型的精度尾巴。 |
| Q5 | 杂项 | 接口文档比实际接口少 15 个左右；SSE 断线重连会丢几条广播；图谱组件超大图会整幅重绘（卡）。 |

### 4.4 压根还没做的能力

| 能力 | 现状 |
| --- | --- |
| 函数多运行时 | 目前只会 FEEL 一种"方言"；说好的 Rhai、Wasm 两种运行时是空占位，调了直接报"不支持"。 |
| 派生属性落库 | 派生属性能**算**出来，但算完**存不了、也不会自动重算**——只能现用现算。 |
| 更硬的权限门 | 行级过滤、字段脱敏有了；但"直接硬拒绝你访问"这类更严格的门还没做。 |
| 索引标记没消费 | 字段可以标"要建索引"，但标记只是存着，物理索引没人建——登记了愿望，没实现。 |
| 性能压测 | 功能全测了，但"1000 人同时用 / 亿级数据"这类压力测试一次没做。 |

---

## 五、一句话总结

**地图画好了、数据能装能查、按钮能办事还能联动审批和报表（351 项测试全过），主体功能是能用的。**

短板集中在两处：一是**安全上有两扇没关严的门**（S1 / S2），应最优先修；二是**自动化断了几根线**——不会定时干活、审批结果回不来、同步不能增量，目前是个"手动挡"平台，踩一脚动一下。把 P0 安全债补上、T1 / T2 / T3 三根线接好，它就能从"能用的工具"升级成"自己会转的机器"。
