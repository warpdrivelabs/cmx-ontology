① 三分钟看懂：两边分别是什么

Palantir Foundry 本体（Ontology）是 Foundry 平台的语义层核心：把湖里的数据「翻译」成业务对象 （客户、订单、工厂、设备），对象之间连成关系网，再配上一层动作（Action）让业务人员能直接在对象上办事、写回数据， 配上函数（Function）承载业务计算，最后用 Workshop / Graph / Map / Object Explorer 等应用直接消费这张网。 官方叫法是「企业的数字孪生 / 语义层」。

CMX 本体平台（cmx-ontology，:8097）走的是同一条路线：六类元模型元素 （对象类型 / 关系类型 / 接口 / 共享属性 / 动作类型 / 函数）+ PostgreSQL 物化（定义表 om_* + 每类型一张 oo_<Type> + 公共边表 ol_edge） + 动作事务与副作用 + 版本快照 + 设计器 / 浏览器 / 工作台三个业务页面。四个 crate 一芯多壳，门户经 OntoProxyModule 反代 /api/onto/*。

关于决策图（cmx-decision-graph）的特别说明

决策图不属于本体平台，是规则引擎（cmx-rulesengine）的前端组件，但它在对标里有一席之地： Palantir 没有独立的「决策图 / 决策表」产品——业务决策逻辑在 Foundry 里就是 Functions + AIP Logic。 本地把决策逻辑独立成规则引擎（决策表 / 决策图 JDM DAG / 仿真台 / 审计中心 / gap-overlap 完整性分析）， 是一套差异化设计，对应能力并不缺；缺的是与本体平台的打通（见矩阵 D-8）。

组件本身的现状：5 类节点（input / output / 决策表 / 表达式 / 子决策）、Kahn 拓扑防环、只读预览模式都已可用， 已被决策图设计器（编辑态）和决策集工作台（只读预览）两个页面消费。 短板：无缩放平移 / 无 undo / 画布内删不了边（无 Delete 键）/ 无导出；注释里写了 fitView 但没实现； 仓库构建依赖兄弟仓工具链；vendor 产物落后于 dist（平台在跑旧版组件）。证据：src/element/cmx-decision-graph.ts、graph-designer.js

④ 还欠缺：按优先级的补课清单

P0 · 安全止血（能不能上生产的分水岭）

S1 主体身份可自报

大白话：门禁系统读的是访客自己填的胸卡——请求里的 subjects 谁都能报，角色还是租户名占位， 再严的策略也形同虚设。对标：Foundry 身份全程不可自报。怎么补：方案已有（主体裁定矩阵：一律忽略 body subjects + HTTP 调 dataauth /decide 拿残差 + 读路径 secure-by-default + fail-closed，[authz] mode=off|local|dataauth 三态开关），约 8-10 人日，未实施。

S2 Funnel 源 SQL 不设防

大白话：源映射里的 sourceQuery 是任意 SQL 且走字符串拼接，能碰到库的人等于拿到后门。 对标：Foundry 管道定义受治理。怎么补：sourceQuery 白名单化（只读 + 表级授权 + 参数化）。

P1 · 性能与调度（决定能不能扛大流量）

索引与调度三件套

  • isIndexed 物理索引消费（Q1）：JSONB 无字段索引，大表过滤全表扫，Palantir 常查属性是自动建索引的。
  • 调度器（T1）：同步、outbox 派发全靠人点；Foundry 有 Automate。最简形态 = 内置 cron 或复用外部调度跑 /funnel/sync 与 /action-outbox/dispatch。
  • 增量水位（T4）：记录上次同步位置，只推变化，别每次全量。

正确性三枚小债

  • 发布并发撞版本号（Q3）；
  • 删对象清边按 pk 全局匹配可能误删同名 pk（Q2）；
  • FEEL 数值走 f64，金额类计算有精度隐患（Q4）。

P2 · 平台能力补课（决定「像不像一个平台」）

可观测与检索

  • 对象编辑历史：逐行属性级「谁在何时改成什么」，Foundry 对象历史是标配；本地只有动作级审计。
  • 全文搜索：pg_trgm + 全局搜索端点 + 浏览器搜索框。
  • 异步任务中心（T5）：大同步 / 批量操作别卡在 HTTP 请求里。
  • SSE 持久化 / MQ：事件掉线不丢、多副本互通（NATS 或共享表兜底）。

建模与执行补全

  • 关系 backing 补全：joinTable / intermediary 实装、foreignKey 写侧落地（现在写侧都兜底边表）。
  • wasm 函数运行时：Extism 插件接入，函数走出表达式级。
  • 聚合扩展：avg / min / max / sum，凑齐 Foundry 常用面。
  • 多分支协作：草稿区从单区到多人分支 + 提案合并（对标 branching）。
  • OSDK 多语言：Python / Java 客户端生成。
  • 地图 / 时序 / 媒体三应用：视业务场景按需上，不建议一口气补齐。

P3 · 生态（决定「能不能长出应用生态」）

AI 与闭环

  • MCP 工具面：把本体端点包成 MCP 工具，让 cmx-agent 能查对象、执行动作——这是本地的「AIP 时刻」，规划随 cmx-agent。
  • 本体感知 AI 助手：基于对象集的自然语言问答。
  • 流程审批结果回写本体（T3）/ 本体 → MDM 回写（T7）：打通双向闭环。
  • 模板市场：动作模板升级为跨域本体模板分发。

横切 · 前端工程债（本周盘点新发现）

三个图组件相关的问题

  • vendor 落后于 dist（两仓都有）：cmx-ontology-graph 与 cmx-decision-graph 的运行时 vendor 产物 md5 与 dist 不一致——改了源码但没重跑 sync，平台现在跑的是旧组件。这是纪律问题，建议把 sync 挂进 build 流程。
  • cmx-ontology-canvas 未交付：LOD 虚拟化大画布已实现，但没进 assets、没有任何页面引用，本体工作室 P1 的一半能力悬在半空。
  • decision-graph 交互短板：无缩放平移 / undo / Delete 键 / 导出；fitView 只有注释没有实现。

⑤ 明确不跟的（有意不做，别当欠账）

不做的事为什么不做
⛔ 不跟 换图数据库Foundry 本体底层同样不是图库（对象存储建在数据湖上）。PG 三组表 + JSONB 同构且运维简单，强行换图库是把简单问题复杂化。
⛔ 不跟 RDF / OWL / SPARQL 标准兼容Foundry 本体也是私有语义层，不走 W3C 语义网标准。兼容收益低、迁移成本高，生态上隔离。
⛔ 不跟 联邦查询用「物化拷贝 + 同步」换「查询时跨源联表」的简单可靠；Foundry 主流打法同样是管道物化而非联邦。
⛔ 不跟 Azure Digital Twins 式 IoT 实时建模设备遥测数字孪生是另一条产品线，不在企业本体场景内。

⑥ 一页纸结论

1. 骨架不用动。四根台柱（元模型 / 对象集 / 动作 / 版本）与 Foundry 同构，60 个能力点里 26 个齐装、15 个有基础， 没有任何一处需要推倒重来。

2. 钱先花在刀刃上。P0 两枚安全债（S1 身份自报、S2 源 SQL 后门）是「能不能上生产」的分水岭，S1 方案已备好未实施； P1 的索引 + 调度 + 增量决定大流量下扛不扛得住。

3. 平台感靠 P2，生态靠 P3。编辑历史 / 全文搜索 / 任务中心补上就有「平台感」； MCP 工具面接上 cmx-agent，就是本地版的「AIP 时刻」——那是对标叙事里最值得押注的一步。

4. 两件本周就能做的小事：① 把两个图组件的 vendor 同步纪律挂进 build（现在跑的是旧组件）； ② 把已实现未交付的 cmx-ontology-canvas 接线进本体工作室。

口径与证据：本地现状按 cmx-ontology main@567efe4（2026-09-11，与 origin/main 同步）代码实测； 22 个 e2e 脚本位于 backend/cmx-ontology/test/e2e/。Palantir 侧按公开文档与 2026-09-08 内部审查口径整理， 逐项以对方公开能力为准，不构成产品承诺。状态统计：✅ 已有 26 · 🟡 部分 15 · ❌ 欠缺 19 · ⛔ 不跟 4（共 60 能力点）。
